# Требования к планировке — SpacePlan AI 0.21.0–0.24.0

02.11.2026. Первый шаг этапа 3 «Constraint Engine»: пользователь задаёт типизированные требования к плану, они сохраняются в проекте и детерминированно проверяются по рассчитанным помещениям после каждого изменения. Это требования пользователя, а не строительные нормы.

## Как использовать

Во вкладке «Комнаты» внизу находится блок «Требования к планировке». Выберите тип и назначение помещения, при необходимости площадь или второе назначение, и нажмите «Добавить требование». У каждого требования есть статус:

- «Выполнено» — по плану требование соблюдено;
- «Нарушено» — есть помещения, которые его нарушают (они перечислены с числами);
- «Нет помещений» — в плане нет помещений нужного назначения;
- «Не проверяется» — план в режиме «Вручную»: без стен нет смежности.

Под каждым требованием перечислены помещения и числа, по которым принято решение: площадь, число дверей, пары соседей. В заголовке показано, сколько требований нарушено. Удаление — значок корзины. Добавление и удаление — отдельные шаги отмены. Требования проверяются заново при любом изменении стен, проёмов и параметров помещений.

Назначение помещения берётся из его сохранённых параметров («Назначение помещения» в инспекторе). Помещение без параметров считается «Комнатой» (`other`).

## Типы

| Тип | Поля | Нарушено, если |
| --- | --- | --- |
| `room-min-area` | `kind`, `minArea` (м², 0 < x ≤ 10 000) | хотя бы одно помещение этого назначения меньше `minArea` |
| `room-not-walkthrough` | `kind` | у помещения больше одной двери — в соседние помещения или наружу |
| `rooms-connected` | `kind`, `otherKind`, `byDoor` | ни одна пара помещений этих назначений не граничит через стену (с дверью, если `byDoor`) |

| `room-max-area` (0.22.0) | `kind`, `maxArea` | хотя бы одно помещение этого назначения больше `maxArea` |
| `wall-fixed` (0.22.0) | `wallId`, `start`, `end`, `thickness` | стена удалена, перенесена, изменена её длина или толщина (направление оси не важно) |

Для `rooms-connected` с одинаковыми назначениями нужно хотя бы два помещения, иначе статус «Нет помещений». «Стена не меняется» запоминает ось и толщину выбранной стены в момент добавления (`fixedWallRequirement`) и проверяется в любом режиме помещений, в том числе в ручном. Это отметка для несущих стен; редактирование она не запрещает, а сразу показывает нарушение.

## Требование к одной комнате и подсветка (0.24.0)

Требования «минимальная площадь», «максимальная площадь» и «непроходное помещение» можно задать для конкретной комнаты: в форме поле «Помещение» предлагает все комнаты с сохранёнными параметрами. Такое требование хранит `labelId` — ссылку на запись `wallRoomLabels`, которая и есть постоянная ссылка на помещение — и проверяет только эту комнату, а назначение берёт из её параметров. В списке требование называется по имени комнаты. Если после перепланировки параметры не привязаны ни к одной комнате, статус «Нет помещений» с подсказкой привязать их заново.

Комнаты, нарушающие хотя бы одно требование, обведены на 2D-плане красным пунктиром (`violatingRoomIds`). Выбранная комната сохраняет обычную зелёную обводку.

`labelId` — необязательное поле в v6: файлы без него читаются как раньше; файл с требованием к комнате не откроет приложение версий 0.21–0.23. Противоречие площадей ищется только между требованиями к одним и тем же комнатам: оба по назначению или оба к одной записи параметров.

## Противоречия (0.22.0)

`findRequirementConflicts(requirements)` ищет требования, которые нельзя выполнить вместе независимо от геометрии. Панель показывает их над списком:

- минимальная площадь больше максимальной для одного назначения — противоречие точное;
- помещение «не проходное», но обязано иметь двери в помещения двух разных назначений — невозможно, если такое помещение одно (при нескольких помещениях требования могут выполнить разные комнаты, поэтому это предупреждение, а не точное противоречие). Смежность и двери считает `findRoomAdjacency` (`ROOM_ADJACENCY.md`).

## Формат v6

`FloorPlan.requirements: PlanRequirement[]`, до 50 записей; ID уникальны среди всех объектов плана (`plan-integrity.ts`). Схема проверяет поля каждого типа строго. Миграция только в памяти: v5 получает пустой список, v1–v4 мигрируют как раньше и тоже получают пустой список; запись в хранилище — после первого успешного изменения. Старый файл (v1–v5), в котором уже есть поле `requirements`, не мигрирует и отклоняется: поле не «благословляется» сменой версии. Экспорт JSON использует v6; приложения до 0.21.0 такой файл не откроют.

## Модель

- `addRequirement`, `removeRequirement` в `plan-requirements.ts` — атомарные операции с полной проверкой схемы; действия редактора `requirement:add` и `requirement:remove`.
- `evaluateRequirements(plan, rooms, adjacency)` — чистая проверка; возвращает для каждого требования статус и находки по помещениям в порядке требований. Числа в интерфейсе берутся только из неё.

## Ограничения

- Пять типов требований и два вида противоречий; более широкий язык ограничений и разбор требований из текста — следующие шаги этапа 3.
- Требование «помещения рядом» относится только к назначениям, не к конкретным комнатам.
- В ручном режиме требования хранятся, но не проверяются.
- Площадь — внутренняя площадь по стенам; геометрическая проверка не является строительной экспертизой.
